## 交付物二：问题本质与产品边界

1. **现有工作流实际解决的问题**：把工程纪律变成可检索、可审计的文本体系——解决「纪律不存在/不可查」。**没有解决**「纪律在执行时刻必然生效」（母仓实测：加载≠照做、散文锚 0/20、B 臂复述判级在场但收口 0/9）。
2. **根因**：文本注入的强制力上限=模型注意力。规则数量与执行可靠性在文本层**负相关**（注意力稀释）。
3. **插件能增加什么**（宿主扩展面实证）：执行前拒绝/审批（pre-execute+guard 单调）、工具面收窄（restrict@agent.ctx）、真值采集（guard/post-execute/request-header）、注入面（systemPrompt.section 动态）、事件观测（session/event 全量）。**插件不能**：阻止非工具路径的模型行为（纯文本回答谎报）、覆盖沙箱外 OS 层操作、保证其他插件不干扰、替代用户对高风险操作的判断（审批 UI 是宿主的，插件只供策略）。
4. **最有价值的待验证假设**：H7（证据驱动收尾）> H1（运行时控制）> H2（状态控制）——理由：E1 已证「收口缺口」是四臂最大行为差异（B/A 0/9 vs C 5/9），且模型自发跳过 gate 的缺口（1/3）恰好需要 H2 的状态机来闭合。

## 交付物三：真实可行的运行时架构

（沿用 roadmap §7 脊柱，按实测修正四处）

```
DSH 宿主原生层（已存在，勿重复造）
  pre-execute/guard(单调拒绝+审批) │ restrict(工具面掩码) │ systemPrompt.section(动态注入)
  session/event(全事件) │ request/header(线缆真值) │ approval(审批UI) │ agent/created(dispose)
插件四子系统（本仓已具形/待建）
  ①任务控制器【待建,v2核心】任务记录+状态机+验收条件持有
    ├─ 已有资产：判级信号提取/L3域/规则包 = 状态机的「风险」维度
    └─ 缺口：状态存储/转换校验/验收条件结构化（E1 证明：gate 只验模型选的命令，
       验不了任务本义——验收条件必须由任务记录持有，不由模型即兴选择）
  ②上下文与能力路由器【T2半成】预算器已做「减法」半边
    └─ 缺口：能力索引/分层注入/去重（轨迹取证新证据：skill-catalog 全量注入 41/43
       会话≈本机20技能描述常驻——这正是「按需加载」的真实靶子，不是假设）
  ③执行控制器【已具形】拦截+gate+预算
    └─ 缺口：turn 级 gate 强制（agent/turn-stopping 宿主接口待探针）、工具包装（未验证）
  ④证据与审计【已具形】exec-log+tally 三源+轨迹取证脚本（本轮）
```

**状态机与工具守卫分开实现、经统一数据模型协作**（任务书 §五之问的回答）：状态机是数据（任务记录+转换校验纯函数），守卫是执行点（pre-execute 读状态做决策）——两者经「任务记录」解耦，已验证的注入式架构（judge/rules/budget 全部依赖注入）自然支持。

| 机制 | 依据 | 难度 | 最大不确定性 | 最小验证 | 失败表现 | 替代方案 |

## 交付物六：修订后版本路线（每阶段 ≥3 问呈批，单批单批走）

### v2「任务控制器+收口强制」（最小运行时控制闭环）
- **目标**：验证结果真实影响任务能否宣告完成；验收条件由任务记录持有。
- **机制**：任务记录（user 原文+目标/约束/验收提取+状态+授权）｜状态转换校验纯函数｜gate 判定接入状态（未 gate→下一任务开工追账或 turn-stopping 阻止收尾）｜验收覆盖判定（验证命令与验收条件的相关性——最低限度=关键词/路径相关+人工标注集回归）。
- **前置**：turn-stopping 可行性探针（第一周）；36 会话轨迹的验收标注集（已有素材）。
- **不做**：能力索引/Skill 按需/跨会话恢复/工具包装。
- **验收**：①新会话任务未收口→下一任务开工被追账（真实会话实测）②标注集上验收覆盖判定 ≥80% 与人工一致③误阻率 <10%④全部现有 9 套回归不破。
- **三问呈批**（草案，届时正式化）：①验收条件提取失败时保守拒绝还是降级放行？②追账式强制（延迟到下一任务）是否可接受为 turn-stopping 不可用时的兜底？③状态持久化位置（会话内存 vs 落盘文件）？

### v3「上下文与能力路由」（H3/H4）
- **目标**：分层注入+按需加载在不降纪律执行效果前提下降低无关上下文（skill-catalog 20 技能是现成靶子）。
- **前置**：v2 状态机稳定（阶段是路由的输入）。
- **不做**：自适应调度/自动压缩。
- **验收**：四指标（token/完成率/必要工具遗漏/返工）对照实测，不只看 token 下降。
- **三问**：呈批时定（索引字段集/过滤 skill-catalog 的授权边界/预算紧张时的保留优先级）。

### v4「错误模型+持久化+降级」（H5/H6）
- 统一错误分类+受控重试+插件故障保守策略+跨会话恢复。验收=错误注入测试矩阵。
### v5「对照实验 n≥5+有效性判定」（H1/H2/H7 终判）
- 四臂（含脱敏对照组）×n≥5×三任务+分风险任务组；按预注册矩阵判定。

## 交付物七：优先级与实施顺序

1. **立即（待批）**：turn-stopping 探针（成本 1 天，决定 v2 形态）——比一切模块优先。
2. **复用**：判级/规则包/预算/gate/遥测/实验基建全部直接进入新架构对应子系统，零重写。
3. **暂缓**：工具包装（高不确定+低收益）、跨平台映射、教训库数据层。
4. **可能不值得做**：为每工具建独立纪律（任务书 §九警告——预算器+类别规则已覆盖主诉求）。
5. **依赖序**：turn-stopping 探针 → v2 状态机 → v3 路由 → v4 错误/持久化 → v5 终判实验。无循环依赖。

## 交付物八：决策摘要

- **原方向正确性**：核心方向（运行时控制）正确且已被 E1 证据强化；**错误在版本语义**（v1.0 被当作发行目标，实际产品核心闭环——任务状态机——还没开工）。
- **需调整**：v1.0 改义为最小运行时控制闭环；T3 从 v1.x 提前；错误模型提前；实验纳入轨迹层取证。
- **插件最值得解决的核心问题**：任务完成条件由谁持有——现在由模型即兴选择验证目标（四臂实证的根缺口），应由任务记录持有+程序校验。
- **最小可用闭环**：任务记录+验收提取+gate 接入状态+追账/turn 强制（一个文件修改任务端到端）。
- **最大技术风险**：turn-stopping 可用性（决定状态机是「阻止者」还是「记录器」）。
- **第一项实施任务**：turn-stopping 探针（待批准，1 天）。
- **已有证据可直接入计划**：A≈D 纯度、gate 三态语义、预算四环、fail 双向、B 臂零收口。
- **必须用户批准**：本路线（尤其 v1.0 改义与 T3 提前）；turn-stopping 探针开工；v2 三问（§交付物六）。
