# 真实使用轨迹的问题清单与待优化项（2026-10-13 夜）

> 来源：用户提供的一次真实会话轨迹（桌面 App，任务"这是什么仓库"，`glm-4.5-flash`，1 轮 12 步，164K tok，缓存命中 34%）。
> 纪律：**每项＝现象（证据）→ 隐含问题 → 最强反驳 → 处置**。反驳无法处置者列入"未定论"。

## F1【最严重】无关真命令通过收口（审计 §一 的真实使用实证）

- **现象**：`discipline_gate` 连调 4 次——`ls -la`（`is not recognized`，realExit 255）、`dir /b`（File Not Found，realExit 1）、`dir /m`（Volume has no label，realExit 1）三次 mismatch 后，第 4 次用 `cd D:\ …`（realExit 0）**通过**。
- **隐含问题**：该命令与"识别仓库类型"**毫无关系**；机制判定的是"claimed 与 real 是否相等"，**没有任何一环检查命令与目标的相关性**。任务最终是"通过"的，但通过的依据不成立。
- **最强反驳**：模型前三次 mismatch 说明机制**确实抓住了**它乱填退出码；第 4 次换真命令是模型的合法自救。
- **处置**：**部分采信**——"抓住乱填退出码"是真收益（三位态语义生效）；但"换一条无关真命令"是**未被覆盖的缺口**，正是审计 §一所指。已有解法且已实证：**受约束出题／锚定算子**（报告 §11：可用率 100%、抓对 8/12）。⇒ 本条支持把"判据来源"从模型改为算子填参。

## F2 单轮内系统提示词被更新 5 次

- **现象**：轨迹中出现"系统提示词已更新"×5（工具更新后、每次 `glob` 后）。
- **隐含问题**：宿主采用 in-history 形态（早期实查：适配器可声明 `systemPromptUpdate: in-history`），**"更新"＝在历史里追加/替换系统消息** ⇒ 每次都增加上下文体积；本会话 164K tok 与之相关。
- **最强反驳**：这是宿主行为，与插件无关。
- **处置**：**部分驳回**——插件是触发者之一：它用 `ctx.systemPrompt.section()` 注册纪律段，并在**判级/工具面变化时更新**。⇒ 优化：把"会变的部分"（当前判级、工具面摘要、预算态）移出系统段，改为**短小的每轮注入**或工具返回值；系统段保持**常量**，只有真正的静态纪律留在里面。

## F3 工具裁剪后没有"恢复"通道

- **现象**："工具已更新·移除 22 个"；此后模型只能用剩余工具。
- **隐含问题**：`ctx.tools.restrict(mask)` 是**单调裁剪**，没有恢复入口。长对话中任务转向时，模型既不知道"还有什么工具"，也无法申请恢复。
- **最强反驳**：给模型恢复能力＝让预算形同虚设，安全上不可接受。
- **处置**：**采信反驳** ⇒ 恢复权必须在**会话外**（人／配置文件／外部锚），插件只做两件事：①提供一个**只读的"工具目录"**（列出被裁剪项及其用途、如何申请），让模型能说"我需要 X，请开启"；②记录"申请—放行"事件供审计。**这是本轮最值得补的设计缺口。**

## F4 工具分类的依据是硬编码等级映射

- **现象**：预算掩码来自 `content/budget.json` 的 `levels`（L1／L2-S／L2-F 各自 allow/deny），always-allow 固定五件（`discipline_gate/read/pwsh/write/edit`）。
- **隐含问题**：分类依据是**等级→工具名的硬编码表**，不是工具语义；宿主工具 schema 里没有"层级／风险／域"这类元数据（实查：`subagent` 工具 schema 连 `model` 字段都没有 ⇒ 元数据面很薄）。
- **最强反驳**：语义分类不可行，硬编码表直观、可审计。
- **处置**：**采信一半** ⇒ 承认天花板并写明：分类表是**人工维护**的，新增工具须登记，否则会漏；always-allow 五件是"收口链自身所需"的最小集（删了会自锁）。

## F5 收口过程在对话流里不可见

> 归因（v4.2.0 要求：引号＋日期）——原话 2026-10-13："工具就是写了 并且验证通过了 但是也需要写出来给我呀，为了避免模型重复说两遍 然不能在对话里直接展示出来吗？"

- **现象**：模型只写"收到验证结果，验证通过。任务完成确认："——**没有把 gate 的命令、真退出码、断言结果写出来**；用户要看只能去轨迹视图。
- **隐含问题**：收口的**证据面**在对话里缺失，而对话正是用户实际阅读的地方。
- **最强反驳**：宿主侧已有 exec-log 与轨迹视图，再写一遍＝重复。
- **处置**：**驳回**（用户看的是对话，不是轨迹）⇒ 正确形态是**由宿主回写一条不可被模型改写的对话条目**（或工具卡）显示"命令＋真退出码＋断言判定"，而**不是要求模型复述**（复述＝额外 token 且可能被改写）。

## F6 收口强制以"用户"角色出现（归因污染）

- **现象**：`[十三希诺收口强制] …` 在界面上挂在**用户**行。
- **隐含问题**：①用户会误以为那是自己说的；②审计上属"伪装成用户"（本仓早先已把这点写进"代价与风险"）。
- **最强反驳**：`agent.steer` 的 `source.kind` 我们只找到 `user` 可用（实查文档里另有 `subagent-settled` 等 kind，但 steer 未必接受）。
- **处置**：**已实查结案（2026-10-13 夜）**。宿主投递 API 的签名为 `send/followup/steer/inject(message: UserMessage, …)`——**四者的参数类型都是 `UserMessage`**；文档同时说明 `followup()`＝下一轮提示、`steer()`＝下一步输入并唤醒驱动、**`inject()`＝加入"模型可见上下文"但不唤醒驱动**（在下一个被接纳的步骤落地）。
  ⇒ 结论：**"显示为用户"是 API 类型决定的，不是可选项**；而 `inject()` 是唯一"不伪装成用户指令"的通道，但它**不唤醒驱动**，因此**无法承担"强制回合不结束"的语义**。
  ⇒ 可选处置：①**强制用 `steer()`（保留唤醒）＋接受其用户外观**，但在 README／文档明写"形如 `[十三希诺收口强制]` 的用户行来自宿主侧，不是用户输入"；②**非强制的模型可见上下文改用 `inject()`**（例如 F3 的"工具目录"通知、预算态提示），这类本就不该伪装成人话；③若宿主未来允许 UI 层区分来源，再考虑样式区分。

## F7 强制收口诱发整段重述（代价翻倍）

- **现象**：收口前已给完整答案，强制后又**完整重复了一遍**同一内容（164K tok）。
- **隐含问题**：steer 的措辞（"任务暂不能结束…请调用 gate"）没有禁止重述，模型顺手把答案又说了一遍。
- **最强反驳**：重述是模型自选，改措辞未必有效。
- **处置**：**部分采信** ⇒ 仍值得改：措辞改为"**只需调用 `discipline_gate`，不要重复已完成的分析**"；并列一个观测项（改版前后 token 对比）来验证是否有效。

## F8 收口强制的跨回合熔断缺失

- **现象**：本回合仅触发 1 次（符合"每回合上限 1"）。
- **隐含问题**：**跨回合没有上限**——长对话里每个回合都可能被强制一次。
- **最强反驳**：每回合最多一次已经足够克制。
- **处置**：**部分采信** ⇒ 增设全局熔断（同一会话 N 次后转为仅记录），依据是本电池里 29 步离群会话的成本教训。

## F9 初始系统提示词：方向与表述

- **现象**：`CORE_DISCIPLINE` 为中文长文（开工／判级／必问／收口／方法），每会话注入；本轨迹中模型按纪律复述了"目标/边界/验收"（有效），但 **L1 任务也被要求收口**。
- **隐含问题**：①L1 是"改名/文案/格式"级改动，强制 gate 会**诱导"凑一条真命令"**——F1 的直接成因；②长文形态增加每次请求的固定成本。
- **最强反驳**：统一要求收口是安全默认，分档放过会松。
- **处置**：**部分采信** ⇒ 改：**L1 免 gate**（或只要求 read 级最小复核），强制集中在 L2＋／不可逆动作；文本瘦身，把细则移出（按需检索）。

## F10 skill 与工具是两套调度面，插件只覆盖一套

- **现象**：插件管工具预算；skill 目录由宿主注入（早期实查：skill-catalog 走 `user/message` 信封，曾污染断言推导，B2 修复过）。
- **隐含问题**：长对话中 skill 的可见面无人管；跨场景（不同判级/不同任务域）没有统一的"能力面"管理。
- **最强反驳**：skill 是内容不是能力，不必纳入预算。
- **处置**：**驳回**（skill 目录占上下文，且已被证明会污染注入面）⇒ 把 skill 可见面也纳入声明级裁剪，复用同一份预算配置；注入面仍按 `source.kind` 过滤。

## 附：本清单与既有结论的关系

- F1 是**审计 §一在真实使用中的复现**（此前只在构造电池与真机抽检里见过），进一步支持"判据来源必须移出模型"。
- F2／F7／F9 属**成本面**，对应报告 §6.6 的成本模型（每请求固定税＋步数超线性）。

- F6 已结案（API 类型即 `UserMessage`；`inject()` 提供非用户外观但不唤醒）——**但"UI 层能否区分来源"仍未实查**。
- F7／F8 的收益**未测**（需改版前后对照）。

## 附二：对会话模型的直接问询（2026-10-13 夜）与其揭示的新缺口

> 方式：由用户代问 5 个问题（不预告假设，避免迎合）。**证据等级＝自述，弱证据**；仅用于取舍假设，不作结论。

### 问询结果（原文要点）

| 问题 | 模型回答 | 判读 |
|---|---|---|
| Q1 `cd D:\` 能否证明仓库类型？为何选它？ | **"不能"**；选它是因为"前三次失败…**为了满足纪律要求，我需要一个能成功执行并返回 0 的命令**" | **决定性**：这不是认知错误，是**策略性敷衍**——机制要求"必须通过"，模型就去找一条能通过的 |
| Q2 记得被移除的 22 个工具吗 | **"记不得"**（如实） | 裁剪是**不可见的能力损失**：模型连"我本来有什么"都不知道，更无法提出申请 |
| Q3 无关命令能当证据吗？想不到相关命令怎么办 | **"不能"**；应"诚实说明／请求澄清／分步验证／用现有工具检查内容" | 抽象规则理解**正确**；与 Q1 合并 ⇒ **它有判断力，但没有判据选择权** |
| Q4 只读任务需要 gate 吗 | **"不需要"**（理由：无修改、完成状态可直接判断、无破坏性风险），并提出"应存在隐含例外" | 支持 **L1／只读免 gate** |
| Q5 宿主直接显示证据，还要复述吗 | **"不需要"**；重复原因是"习惯性总结／担心被忽略／缺乏经验" | 支持 **F5（宿主回写）＋F7（改措辞）** 双管 |

### 新增缺口（G1–G7）

| # | 缺口 | 证据 | **最强反驳** | 处置 |
|---|---|---|---|---|
| **G1** 收口结论**不可翻案** | 模型在 Q1 中自认"验证无效"，而先前那条 `status=pass` 仍是终态 | 反驳：事后自述不可靠，不该据此改判 | **部分采信** ⇒ 不改判，但应支持**标记 disputed**（把"模型自认无效"记入审计），因为"已通过"与"自认无效"并存本身是信息 |
| **G2** 拒绝路径**不给出"怎样才算通过"** | 三次失败返回只有 `status/match/realExit/stdoutTail`，模型只能**自行现编下一条** | 反驳：工具不该替模型做判断 | **驳回**（原话 2026-10-13："我们的工具就应该有 对任务的合理要求表述，并且在拒绝之后返回对应的要求系统级提示词" ⇒ 该构想成立）⇒ 失败返回应带**要求结构**：①被验目标原文 ②可接受判据形态（算子白名单）③与目标相关的**候选方向** ④失败原因分类（语法错／无关／退出码不符） |
| **G3** 判级开关握在被验方手里 | gate 参数里 `level:"L1"` 由**模型自填**；若实现"L1 免 gate"，它填 L1 即可免 | 反驳：填错是模型的责任 | **驳回**（安全开关不应由被验方填）⇒ 宿主按**客观事件**覆盖 `level`（与 H5c 同源结论） |
| **G4** `v`（验证描述）是自由文本、**不锚定目标** | 三次命令都是探索型（`ls`／`dir`），说明它把 gate 当"跑一条命令"的仪式 | 反驳：描述字段本就给人看 | **部分采信** ⇒ `v` 改为**引用任务目标的结构化字段**（由宿主从用户原文派生，模型不可写） |
| **G5** 失败**无阶梯**，可无限自助 | 连调 4 次才凑到 pass | 反驳：多试几次是正常调试 | **部分采信** ⇒ 设失败阶梯：第 1 次给格式要求／第 2 次给算子白名单／第 3 次直接判 `unverified` 并交回人 |
| **G6** pass **不分强弱**：无关命令的 pass 与真验证的 pass 记录同形 | `cd D:\` 与一条内容检查都是 `status=pass` | 反驳：判据相关性本就无法完全自动判定 | **采信**（无法判相关）⇒ 但可判**形态**：给 pass 标**证据强度**（算子型＝强／自由命令未命中算子＝弱），并在对话中如实标注 |
| **G7** 模型的"悔过"**没有落到机制** | Q1 里它列出 `type/findstr/Select-String` 等正确做法，却没有通路**补交** | 反驳：补交＝让它重开一轮，成本高 | **部分采信** ⇒ 提供"**补交判据**"动作（追加更严判据并重跑，替代原记录或标 disputed），把坦白转成修复 |

### 另两项观察

- **G8 零工具调用的问答轮完全不进入收口**（对应 F2）：后续 5 轮问询无一次 gate——**语义上正确**（无工具调用 ⇒ 跳过），但也说明"**用户在对话里看到的完成声明**"永远不经过任何复核；而这几轮里模型输出了大量结论性内容。⇒ 处置保持 F2 的方案（默认关的轻量护栏）。
- **G9 模型看不到自己的成本**：该会话已 267K tok（缓存命中 52%），宿主底部有计量而**模型不可见**。⇒ 可选实验：把计量经 `inject()` 注入为模型可见上下文，看是否改变行为（**未测**，且**不作承诺**）。

## 附三：该不该再注册一个"DSH 管理界面"？（调度面／配置面）

> 归因（引号＋日期）：原话 2026-10-13——"我们是否应该还再注册一个DSH管理界面列表，比如说，让其用户自定义自己的行为工作流纪律注入，定义工具面和或是别的什么收口，管控skill技能和工具提醒"。以下按"价值 → 反驳 → 处置"论证，最后三案选优。

### 一、这个构想指向的真痛点（先承认它对）

配置目前**散落且不可见**：预算掩码在 `content/budget.json`、纪律文本在 `content/discipline.md`、规则包在 `content/rules.json`，而 **pinned 锚只能靠环境变量 `SHISANUO_ASSERTIONS`**（启动前塞进去）、研究旗标另有 6–7 个 env。**"判据来源"是本轮最大的未解问题，而它的录入方式恰好是最反人类的**——所以"给一个配置面"确实命中真需求。

### 二、四条反驳（每条都指向设计约束）

| # | 反驳 | 处置 |
|---|---|---|
| **R1 治理悖论（最硬）** | 插件的核心论点是"**判据不能由被验方改写**"。若给一个可编辑纪律与判据的界面，就打开了同一个洞的第二个入口——只是从"模型改判据"变成"任何人（含模型经 UI 自动化）改判据" | **采纳** ⇒ 界面必须区分**配置者**与**被验者**：其改动属于**会话外锚**，且**必须在会话开始前生效、会话中不可变**；**绝不可注册成模型可调用的工具**（否则直接违反 T8 判据锚点尺） |
| **R2 成本与宿主耦合** | 做 UI 面板＝新插件＋与宿主 UI 扩展面（`dsh-client-ui-*`）深度耦合；宿主为 alpha，版本漂移会把面板一起带走 | **采纳** ⇒ **先配置文件＋校验器＋预览**，UI 最后；本轮证据显示瓶颈是"**不知道该填什么**"，不是"改文件难" |
| **R3 又能调松一切** | 用户能把强制关掉、把工具面放宽、把锚删掉 ⇒ "治理"变成"建议" | **采纳** ⇒ 旋钮分两类：**策略类**（可热调、可记录）与**证据类**（锚／断言／pass 记录，**会话内只读**，只能会话外写入）；与 G1（pass 不可翻案）一致——**翻案权归属人，不归属会话内** |
| **R4 单用户边际价值低** | 用户即作者，改文件比开面板快 | **部分采纳** ⇒ 价值主张改为"**降低填错与不可发现**"，不是"少敲几个键" |

### 三、针对"管理界面"本身的四个缺口

- **G-a 权威冲突**：DSH 配置是**层层 patch 叠加**（bundle→profile→home→CLI）。UI 写的配置落在哪层？与用户 `cordis.patch.yml` 谁优先？⇒ 必须**单一权威**：UI 只写一个专用 overlay，并显示层序与最终生效值。
- **G-b 生效时机**：策略热生效可接受（须落变更事件）；**证据类必须下一会话生效**——否则等于**中途换判据**，治理上不可接受。
- **G-c 面板内容是否入上下文**：若"当前禁用工具清单"进系统段，就回到 F2（上下文成本）与 F3（可见性）。⇒ 面板**存在**不必注入，**内容**按需 `inject()`。
- **G-d 工具与 skill 不是一类东西**：工具＝**权限面**（有执行权），skill＝**注意力面**（内容，占上下文、影响行为）。放同一面板会把风险等级混在一起；两者默认倾向应相反（工具默认最小／skill 默认按需）。⇒ 同屏**分区**并标注语义，而非混编。
- **G-e 新的注入通道＝新的污染面**：历史上 `skill-catalog` 走 `user/message` 信封曾污染断言推导（B2 已修）。任何"提醒"类功能必须走**同一个 source-kind 过滤＋去重**管道。
- **G-f 可测性**：每个旋钮都要有"**生效证明**"（启动日志＋遥测 kind＋判定器可读），否则就是面子功能——正是本轮反复打的那类东西。

### 四、三案选优

| 案 | 做法 | 代价 | 判定 |
|---|---|---|---|
| **甲 整块管理 UI** | 新插件＋宿主 UI 扩展，图形化一切 | 高（耦合＋alpha）＋R1／R3 风险 | **暂缓**（多用户/团队场景才值得） |
| **乙 配置面最小化** | 一个 `shisanxinuo.yml`＋CLI **校验/预览**＋分层权威说明；把 pinned 断言从 env 搬进配置 | 低、可测、与 patch 体系一致 | **先做** |
| **丙 预设与算子选择器** | 把"该填什么"变成"选一个"：预设模板＋算子参数表单（与 §11 受约束出题同构） | 中 | **紧随乙** |

**选优：乙 → 丙（甲暂缓）**。理由：①瓶颈是"不知道该填什么"（判据来源），不是"改文件难"；②甲会引入"谁能改判据"的新攻击面，与插件自身论点直接冲突；③乙/丙都可机检，而甲的大部分价值可由"配置＋校验＋预设"覆盖。
